# Автотесты для веб-сервиса `/endpoint`

Тесты для Spring Boot приложения из тестового задания (LOGIN / ACTION / LOGOUT с внешним сервисом `/auth` и `/doAction`).

**Стек:** Java 17, JUnit 5, WireMock 3, REST Assured, AssertJ, Allure 2, Maven.

## Быстрый старт

Нужны Java 17+ и Maven 3.9+.

```bash
# 1. Положить jar приложения в папку app/ (сам jar в репозиторий не входит)
cp /path/to/internal-0.0.1-SNAPSHOT.jar app/

# 2. Запустить все тесты. Приложение и «внешний сервис» (WireMock) поднимутся сами
mvn clean test

# 3. Открыть отчёт Allure
mvn allure:serve          # либо: allure serve target/allure-results
```

Полезные варианты запуска:

| Команда | Что делает |
|---|---|
| `mvn test -Dgroups=smoke` | быстрый дымовой прогон (главные сценарии) |
| `mvn test -DexcludedGroups=defect` | всё, кроме тестов на известные дефекты — «зелёная» регрессия |
| `mvn test -Dgroups=defect` | только тесты, подтверждающие найденные дефекты |
| `mvn test -DexcludedGroups=slow` | без тестов на зависание внешнего сервиса (они идут ~10–15 с) |
| `mvn test -Dapp.jar=/другой/путь/app.jar` | другой путь к jar |
| `mvn test -Dapp.start=false` | приложение уже запущено вручную (с `-Dsecret=qazWSXedc -Dmock=http://localhost:8888/`) |

Все настройки — в `src/test/resources/config.properties`, любую можно переопределить через `-D`.
Порты `8080` (приложение) и `8888` (WireMock) должны быть свободны.

> **Важно про результат.** Тесты на найденные дефекты (тег `defect`) **специально красные**: они проверяют поведение
> «как должно быть», а приложение ведёт себя иначе. В отчёте Allure они попадают в категорию
> «Дефекты тестируемого приложения». Остальные тесты должны проходить.

## Что покрыто

Около 120 проверок (с учётом параметризации) в 11 классах:

| Область | Класс | Что проверяем |
|---|---|---|
| Защита API-ключом | `ApiKeyTest` | нет ключа / неверный (регистр, длина, пустой) для всех трёх действий; ключ проверяется раньше остальных параметров; отклонённый запрос не создаёт сессию |
| Токен | `TokenValidationTest` | граничные значения: 31/32/33 символа, регистр, пробелы, спецсимволы, кириллица, SQL-инъекция; невалидный токен не доходит до внешнего сервиса |
| Параметр action | `ActionParameterTest` | только `LOGIN`/`ACTION`/`LOGOUT` и только в верхнем регистре; отсутствие параметров |
| LOGIN | `LoginTest` | успех, контракт запроса к `/auth`, любой 2xx = успех, тело ответа игнорируется, 4xx/5xx = неудача и токен не сохраняется, дубль (409), повторный вход после выхода и после сбоя |
| ACTION | `ActionTest` | без входа 403, после выхода 403, многократные вызовы, контракт запроса к `/doAction`, сбой внешнего сервиса не рушит сессию |
| LOGOUT | `LogoutTest` | успех без обращения ко внешнему сервису, повторный выход, независимость пользователей, работа при недоступном внешнем сервисе |
| Сквозные сценарии | `SessionScenarioTest` | полный жизненный цикл, два независимых пользователя, восстановление после сбоя |
| Сбои внешнего сервиса | `ExternalServiceFailuresTest` | обрыв соединения, пустой ответ, мусор в ответе, зависание (таймаут), медленный, но допустимый ответ |
| Конкурентность | `ConcurrencyTest` | 20 параллельных LOGIN одним токеном (успешен ровно один), параллельные LOGOUT, LOGIN разных пользователей |
| Корректность HTTP | `ProtocolHandlingTest` | неподдерживаемые методы, неизвестный путь, JSON вместо form-urlencoded, параметры в URL |
| Формат ответов | `ResponseFormatTest` | JSON и `result=ERROR` + `message` для каждого вида ошибки; нет утечки внутренних деталей |

**Техники тест-дизайна:** классы эквивалентности и граничные значения (токен, action), тестирование переходов состояний
(токен: «нет сессии» ⇄ «вошёл»), таблица решений по кодам внешнего сервиса, предугадывание ошибок (инъекции, гонки, таймауты).

Модель состояний, которую проверяют тесты:

| Состояние токена | LOGIN | ACTION | LOGOUT |
|---|---|---|---|
| нет сессии | `/auth` → 2xx: **OK**, сессия создана; иначе ошибка, сессии нет | **403** | **403** |
| есть сессия | **409** (`/auth` не вызывается) | `/doAction` → 2xx: **OK**; иначе ошибка, сессия сохраняется | **OK**, сессия удалена (внешний сервис не вызывается) |

## Как устроен проект

```
src/test/java/com/example/aqa/
├── config/   TestConfig — настройки (config.properties + -D)
├── infra/    EnvironmentSessionListener — один раз на прогон поднимает WireMock и приложение
│             ApplicationProcess — запуск jar, ожидание готовности, остановка
│             ExternalServiceMock — обёртка над WireMock: заглушки и проверки «что получил внешний сервис»
├── client/   EndpointClient — клиент POST /endpoint (REST Assured) со шагами Allure
│             Checks — проверки с формулировками на человеческом языке
│             ApiResponse — разобранный ответ
├── data/     TokenFactory — уникальные валидные токены
└── tests/    тесты по областям; BaseApiTest — общие правила
```

Ключевые решения:

- **Тесты независимы и идут параллельно** (8 потоков). У каждого теста свой случайный токен, а заглушки WireMock
  привязаны к телу запроса `token=<токен теста>` — поэтому тесты не видят чужих запросов и не требуют `reset()` общего состояния.
- **Окружение поднимается один раз** через `LauncherSessionListener`: никаких ручных шагов и зависимости от порядка тестов.
- **После каждого теста токены разлогиниваются**, так что повторный запуск на уже работающем приложении (`-Dapp.start=false`) не даёт ложных 409.
- **Проверяем не только ответ, но и побочные эффекты**: сколько запросов и в каком формате получил внешний сервис
  (в том числе что не получил ни одного там, где не должен был).
- **Нет `Thread.sleep` и ожиданий «на авось»**: приложение синхронное, а задержки внешнего сервиса задаются в WireMock.
- **Отчёт для нетехнического читателя**: названия, описания и шаги на русском («Проверить: сервис ответил ошибкой…»),
  группировка по функциям, серьёзность (blocker → normal), HTTP-запросы и ответы приложены к шагам, окружение и категории дефектов — в отчёте.
- Разбор статусов ошибок внешнего сервиса (4xx и 5xx) строго по документации: приложение смотрит **только на код**, тело игнорируется — это тоже проверено.

## Найденные дефекты

Подтверждены на приложении `internal-0.0.1-SNAPSHOT.jar`.

| ID | Серьёзность | Описание | Ожидалось | Фактически |
|---|---|---|---|---|
| **BUG-01** | Critical | Токен проверяется по `^[0-9A-F]{32}$`, а в документации разрешён диапазон `A-Z0-9`. Токен `ZZZZ…Z` или `GHIJKLMNOPQRSTUVWXYZ012345678901` отвергается | `200 OK` | `400 token: must match "^[0-9A-F]{32}$"` |
| **BUG-02** | Normal | Ошибки клиента дают `500 Internal Server Error`: методы GET/PUT/DELETE/PATCH на `/endpoint`, несуществующий путь, JSON-тело вместо form-urlencoded, параметры только в URL | `405` / `404` / `400`–`415` | `500` |

Тесты: `TokenValidationTest#tokenWithLettersGToZIsAccepted`, `ProtocolHandlingTest`.

## Наблюдения (не считаем дефектами, но стоит уточнить у автора требований)

1. **Любая ошибка внешнего сервиса превращается в `500 Internal Server Error`** с общим сообщением — и `401/403` от `/auth`
   (по смыслу «вход отклонён»), и `503` (сервис недоступен), и таймаут. Клиент не может отличить «неверные данные» от «сбой». Возможно, `401` и `502/503` были бы точнее. Тесты проверяют «ошибка и токен не сохранён», не фиксируя конкретный код.
2. **Таймаут внешнего вызова ≈ 10 с, без повторных попыток.** Тест на зависание ждёт ошибку не дольше 20 с.
3. **Код 3xx от внешнего сервиса считается успехом** (при ответе `302` без `Location` вход выполняется). В документации про это ничего нет.
4. **`action` обрезается по краям (`"LOGIN "` принимается), а `token` — нет** (токен с пробелом отклоняется). Непоследовательно, но безобидно.
5. **`Accept: text/html` даёт `406` с HTML-страницей Whitelabel**, а не JSON.
6. **Токены пишутся в лог приложения и в тексты ошибок открытым текстом.** Если токен — секрет сессии, это риск.

## Что можно улучшить дальше

- CI (GitHub Actions / GitLab CI): достаточно добавить шаг, который кладёт jar в `app/`, и запуск `mvn test` с публикацией отчёта Allure.
- Выделить тесты на дефекты в отдельный профиль Maven, чтобы «зелёная» регрессия не смешивалась с «красными» проверками багов.
